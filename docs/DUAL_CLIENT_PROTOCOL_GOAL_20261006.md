### 資料表共用政策

使用者進一步確認兩版遊戲內容相同：**共用所有遊戲內容與權威資料表為預設**，涵蓋角色、怪物、技能、道具、任務、地圖與經濟。不同封包長度／位元排列優先在適配器轉換；不得只因TW/CN版本不同就複製兩套資料表。下表的版本專屬儲存僅用於已找到實際無法共用的資料，不能把可能差異當作拆表依據。

| 資料 | 優先採用 | 版本差異處理 |
|---|---|---|
| 帳號身分／密碼驗證 | 既有 `accounts` 與Repository | 本輪已接唯讀既有帳號；不匯入獨立 `cn_accounts` 或其不同密碼hash前綴 |
| 角色權威ID／帳號所有權／金錢／物品持有／公會關係 | 語意相符時共用既有權威資料與交易 | 欄位名稱相似不足以認定可共用，需確認單位、範圍與玩法規則 |
| 地圖／技能／道具等內容資料 | 共用內容表與同一套權威ID | 僅已證明不同的客戶端ID在適配器對照；不預先拆成TW/CN內容表 |
| 已證無法共用的原生raw快照／專屬資料 | 最小範圍版本專屬儲存 | 優先用適配器處理；確需新表才使用 `_tw`／`_cn` 後綴，例如 `character_snapshot_tw`／`character_snapshot_cn`，外鍵指向共用權威ID |
| 混合身分與raw資料的舊表 | 保留既有ID／FK／表名及原始內容 | 逐步抽出版本呈現，不能先重命名或把固定layout當共用模型 |
| 文字 | 可共用的權威UTF-8文字 | codepage、byte限制及名字辨識條件在版本邊界處理 |

尤其 `recovered_characters.profile` 有固定40-byte CHECK，`name_bytes`有台服既有bytes規則；原生陸服07角色摘要stride36也不等於可覆寫此表的profile。`characters`另含早期fixture欄位預設，不能為了共用而偷偷把它升為正式原生角色表。角色共用需保留現有權威ID和引用，待欄位語意恢復後建立合適映射。本輪未執行schema遷移或讀寫正式資料庫。

後續先完成CN帳號成功與選服、角色列表的原生欄位，再將admission／世界命令接到共同權威服務；各新增版本專屬表遵循以上後綴政策。使用者指定版本標記放在表名尾端，便於日後在MySQL等資料庫按共同表名尋找；共用表不加版本後綴。

## 版本分流實作邊界

1. 先取得使用者指定的陸服客戶端完整安裝目錄或可重現的版本來源，唯讀記錄 EXE、相關 DLL、資源與設定的 SHA256。來源不完整時保留缺口，不把語系、檔名或舊版本號當協定指紋。
2. 對兩版逐狀態比對初始握手、登入／角色／世界入口、外層 framing、加解碼／checksum、C2S producer、S2C consumer、欄位、長度、子型別與遊戲狀態門檻。相同 opcode 在兩版也要獨立證明方向與語意。
3. 服務端每個 Session 固定一個已證明的客戶端協定版本，C2S 解碼和 S2C 編碼成對切換，交給共用的帳號、角色、世界、戰鬥、Lua 規則與 SQLite 狀態。若握手前無可信的同埠識別位元組，使用兩個明確配置的接入埠；不得以 IP、語系、帳號或猜測內容自動改派版本。
   現有 `Application.cpp` 已把登入與角色／世界連線分成兩個 `TcpServer`，`TcpServer` 再以固定 `ProtocolMode` 建立 `Session`。因此陸服若採獨立接入埠，也須保留其登入埠到角色埠的成對路由，並共用原本的遊戲執行緒與持久狀態；僅在 `Config` 增加埠號而沒有陸服 Session 解碼／編碼，不構成封包串接。
4. 只有已復原的陸服封包路徑才可接進正式來源。未知格式與歧義請求須明確拒絕，不使用空處理器、台服回包假冒陸服格式或通用成功回覆。舊台服路徑保持固定；共享業務邏輯的變更必須保留版本邊界。
5. 路徑帳本增加按版本的 producer／consumer、登入／世界／戰鬥狀態、變體、來源接入與回覆關聯。兩版完成度分開列示；共用來源分支不能自動算作陸服封包已接。完成所有路徑後，才依既定階段做雙客戶端全方位驗證、修復與發布。

## 目前進度與下一個可執行步驟

台服現有來源盤點以最新 `packet-progress-latest.md` 為準；陸服已證雙向來源路徑為 **0**，陸服全遊戲分母 **未知**。本輪未更動協定程式、未部署，也未執行測試。取得指定陸服客戶端後，先釘定其初始握手與登入／角色入口，據實決定同埠識別是否可能；否則採獨立接入埠進入同一服務端，再展開 WORLD／戰鬥雙向封包清單與版本轉接。

## 架構分析與採用方案

以下是來源分析後的設計決策，尚未實作或證明陸服相容。

| 方案 | 優點 | 對本專案的限制 | 決策 |
|---|---|---|---|
| 把陸服封包直接轉成台服封包 | 簡單的 opcode／欄位差異可局部轉換 | 狀態流程、不同資料模型、多人回覆及資源差異會迫使轉換器模擬整個客戶端；雙重編解碼 | 不作主架構；只在已證等價的個別格式重用 |
| 兩套独立遊戲服務端共用資料庫 | 各自接客戶端較直接 | 記憶體世界、戰鬥房間、交易及鎖不會因共用 SQLite 自動同步 | 不採用 |
| 單一服務進程，兩套協定前端，共用權威遊戲核心 | 兩版玩家能共用世界、交易及戰鬥，協定差異集中 | 需逐步把目前直接建包的業務分支拆為語意事件及版本呈現 | 採用 |

第一版採明確分埠的版本入口；各版本維持原生所需的登入／角色／世界連線流程，不要求兩版使用相同連線數。現有台服在 `Session::Impl::start()` 接受連線後便主動送出 19-byte hello；陸服初始 hello 未知，所以目前沒有依據讓服務端等候共同的首包再猜版本。同埠自動識別只能在兩版原生初始流程證據足夠後列為後續優化，不能成為雙版本開發的前置障礙。

所有入口進入同一帳號服務、權威角色／世界／戰鬥狀態及遊戲執行緒；跨版本互動用角色身分和場景／戰鬥實例身分關聯。登入端分流與角色端分流成對配置，重新認證及角色權限檢查仍經原有服務，不能只憑客戶端選到某埠就授權。

### 收送資料模型

建議資料流：版本 C2S 位元組 → 對應 framing／checksum／解碼／狀態檢查 → 共用型別化命令 → C++ 權限、交易與持久化／Lua 規則 → 共用遊戲事件 → 每個接收者的版本呈現 → 對應 S2C 編碼與發送。

例如台服玩家攻擊陸服玩家，核心只結算一次傷害、資源、狀態和掉落；台服觀察者收到台服戰鬥事件序列，陸服觀察者收到陸服事件序列。一次動作可對應各版不同數量、排序及 ACK 門檻的封包，不假設一對一 opcode 轉換。

新增的版本設定應把 `ProtocolDialect`、`ClientBuildId`、`ContentRevision`、`TextEncoding`、`Capabilities` 分開；名稱是設計提案而非已存在程式。EXE 雜湊用於本地證據及啟動器版本選擇，不是服務端能從 TCP 自動信任取得的證明。端點綁定協定版本，字元編碼只是該版本的一項設定。

### 原始碼需處理的實際接點

- `src/core/Config.h/.cpp`：版本入口與其角色路由成組配置；保留既有台服預設，避免為缺少陸服 codec 的配置開出可用入口。
- `src/net/TcpServer.cpp`、`src/net/Session.h/.cpp`：每個連線固定協定版本、對應的分包緩衝／狀態機／回包佇列；保留全域 Session ID、背壓、斷線清理與世界／戰鬥代次檢查。跨入口仍需總連線上限。
- `src/protocol/RecoveredWorldRecords.h`：現有解析結果含版本相關型別，應逐功能映射至共用命令，未知欄位保留其版本來源。
- `src/core/Application.cpp`：目前多處直接呼叫 `RecoveredWorldFrame::encode`，回呼亦有直接返回已封裝回覆的路徑；不能只改 `Session::send_world_records`。直接回覆與主動推送都要經接收者版本呈現。
- 現有 `party_projection` 已先取得遊戲事件再逐收件者產生文字及回覆，可沿用其分層模式擴展協定呈現。交易、場景可見性、公會、戰鬥及重連快照同樣須覆蓋。

採逐功能接入：把既有台服建包器包入台服呈現分支，新增陸服呈現分支，共用既有業務服務。不要先大改整份 `Application.cpp` 或另造第二套權威玩法；只有受版本差異影響的接點才拆分。

### 封包以外的相容範圍

資源／內容清單必須比較地圖、NPC、怪物、道具、技能、模型、動畫、音效、UI、欄位範圍及 ID。內部使用穩定的伺服端身分，各版資源 ID 透過有證據的對照表呈現。不能靠名稱相似就認定同一技能或怪物。

若其中一版完全缺少地圖、動畫或操作 UI，封包轉譯本身無法補出內容。初期跨版共玩範圍須有明確能力矩陣：可完整對應的共用、只有呈現差異且已證可等價的才轉換、無法表達的互動在扣款／交易／入場前拒絕，直到取得相容資源及相應授權。不得靜默替換技能效果或改寫玩家物品；完整雙版本遊戲目標仍保留這些缺口。

資料庫目前含 `logical`、`logical20` 等原生快照與道具 metadata（例如 `SqliteBeastSnapshotRepository.h`、`SqliteWorldDisplayRepository.h`、`SqliteArmorSlotRepository.h`）。其內容不能直接視為兩版通用存檔。已知語意欄位逐步接到共用模型；未知 bytes 保留原樣並綁定來源版本，尚未有陸服映射時不向陸服重播台服 raw snapshot。新增版本映射應採附加資料與可回復遷移，不全面重写既有存檔。

名字與文字另行處理字元編碼、byte 長度、不可表示字元、截斷及碰撞；權威角色身分不能依轉碼後顯示名。現有組隊原生協定會以名字辨識自己，必須保留它的精確名字條件，不能任意繁簡轉換。

### 執行順序及最後驗收

1. 取得指定陸服安裝目錄，釘定版本；產出雙向封包、狀態、內容及能力差異表。先定位握手、登入、角色、進世界，隨後完整盤點 WORLD 與戰鬥。
2. 接版本前端和成對登入／角色路由，保留單一權威核心；先串身分／世界／移動，再串背包／經濟／交易、隊伍／公會、戰鬥／技能／寵物、任務及其餘全部變體。每個功能同時處理主動回覆、對其他玩家的推送及重連恢復。
3. 依使用者要求，來源串接階段不執行逐項測試或原生驗收；静態逆向與來源盤點繼續。每輪按版本、方向、狀態、變體列新增接入與缺口。
4. 全部路徑接完後集中測試 TW→TW、CN→CN、TW→CN、CN→TW，以及混合隊伍／戰鬥／交易、重連、取消與失敗分支；以兩版真實客戶端的操作、呈現及權威資料一致性驗收，再做全面修復／回歸與發布。

上述初期分析當時尚無陸服執行檔；後續已釘定CN原生版本及承接來源，詳見本檔前段和PACKET_CONNECTION_GOAL_20261006.md。全遊戲分母仍未封閉，不能估計完成百分比或宣稱兩版能完整共玩。
