# Combined terminal progression transaction

The optional BattleProgressionCommit extends settle_battle with expected XP
(including absent-versus-zero), expected complete role snapshot and next complete
role snapshot. This is a trusted server API, not a client payload. The C++ caller
must evaluate authorized growth in Lua; storage does not invent that rule.

Canonical request version2 includes those inputs and every role byte/provenance.
Caller-supplied next revisions are normalized and generated by storage. Calls
without progression retain their EXACT version1 request shape, so prior saved
zero/award settlement retry contracts remain compatible.

Under one BEGIN IMMEDIATE the repository verifies reservation ownership,
resource snapshot, XP baseline and role snapshot; stages role/resources; adds
experience; inserts terminal ledger; reads back all four records; and commits.
The role-resource helper has been factored to run inside an existing transaction
without nested BEGIN. Its standalone public wrapper retains prior atomicity.

Exact replay returns recorded resource/XP and reconstructed role snapshot with
its assigned revision. It never rewrites newer state. Changed base stats,
growth payload, expected XP or omission of a previously bound role fails request
equality. An accepted historical reply is not the latest current character state.

## Tests

Existing repository cases now also exercise a full role-bearing terminal write:
synthetic level3->4, explicit maxima50/10->70/20, HP retained and MP5, test award25.
No native growth or balance value is inferred from these operands. Cases include
stale XP, stale role, exact retry, changed stat byte, retry without role payload,
and replay after a later HP debit. Triggers fail or corrupt role/XP at the last
ledger insert; all resources, role, XP and ledger must remain at their old state.
Legacy resource/award/role transactions remain covered by existing tests.

Follow-up disk/concurrency qualification: test_settlement_reopen_and_contention
now executes both the legacy request and role-bearing request against separate
temporary on-disk databases. Role-bearing setup persists level1/revision1 and
closes the database before opening two independent connections. Both race the
same terminal request. Each returns identical level2/revision2, resources with
exactly one revision increment and totalXP25. Closing both connections and
opening a third retains the complete role bytes/resources/XP; an exact retry
returns the same historical result, a changed award fails, and only one ledger
row exists. The suite passed10 consecutive runs. This is close/reopen durability
and connection contention, not process-kill/power-loss or live login acceptance.
