# CN native19 current offered identity to shared character ownership

PHASE1 source integration only: no build, test, client/server execution,
production DB access, migration or deployment. Previous goal turn is progress:
the saved delete-return/UI/control evidence changed which result may establish
local list compaction. This increment connects the prerequisite identity layer
in C++ source; it does not introduce a deletion transaction or generic success.

## Source implementation

SharedCharacterDeleteIdentity resolves a parsed native19 only against the
current committed world's actual OfferSource. The shared admission record
already carries original07 bytes and common character IDs in exactly that row
order from SharedAccountSelection. Those fields are supplied by the real native
summary source; this increment does not fabricate that source or infer common
IDs from names, ordinals, protocol slots or the TW40-byte profile.

The resolver requires the World transport role, verified account, nonzero
world-session identity, current committed offer, exact full07 bytes/ID order,
unique nonzero common IDs and unique low3 native slots. It reads the actual
RecoveredCharacterRepository and requires every offered common ID to occur
exactly once with this verified account. Native19's slot selects the unique
advertised07 row. Its character name must then match that row's original bytes.
Names are echo checks after slot/ID ownership resolution, never DB lookup keys.
No client credential bytes are retained, logged or sent to Lua by this value.

Identity construction additionally requires actual owner-supplied credential
and current pre-world phase predicates. Returned values have no public identity
constructor. They retain a weak reference to the exact connection, its account/
world-session, original offer bytes and ordered IDs, target common ID/native
slot and the owner's phase predicate. current() repeats the connection, current
committed offer, row association, phase and current repository ownership checks.
Grant generation/reservation checking remains in the existing connection's
ticket-bound shared admission methods; no old ticket is copied into a new one.

The caller must keep the repository alive and use its serial game executor.
This is an identity snapshot with rechecks, not a consumed operation token or
atomic permission/CAS. Repeated identity resolution cannot by itself authorize
multiple deletions. Real transaction rules, online/resource restrictions,
current save revisions and duplicate/replay handling remain required.

## Existing pre-world owner entry

SharedWorldSelection now exposes resolve_deletion_identity(record). It accepts
only the full54-byte native19 view and delegates to the common resolver using
its existing authenticated CredentialAlias list. Its weak phase predicate
requires the same currently qualified offer, no pending/started1A, and no
selected gameplay ingress. Credential aliases remain byte-preserving; they are
not created from this19, translated or compared as display text.

An additive offer_queued_ flag is set only after the complete1F send_batch result
returns accepted and the existing offer ownership checks still pass. The new
identity entry requires that flag. Queue acceptance is not native reception or
playability. Entering1A invalidates the new identity through existing state;
transport close/release, changed offer, lost common ownership or owner expiry
likewise prevents its current() check. No1A success, queue ordering or frozen
authentication behavior is changed by this additive entry.

Native19's low3 slot domain is0..7 in the independent resolver. Existing normal
NativeOffer creation still requires its separately qualified1A slots below4;
this increment does not relax that limit or claim high-slot deletion is hosted
through that existing selection controller. Other pre-world issuers/owners need
their own actual phase and credential predicates. Transfer1F slots do not
replace07's deletion slot/ordered common-ID lineage.
