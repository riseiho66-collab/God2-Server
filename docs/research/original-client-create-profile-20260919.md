- `0xC168` / `0xC177` copy 40 bytes from main object `+0x15280`.
  `0xC181` increments byte 29, `0xC19D` increments byte 31;
  `0xC183..0xC19F` replace word 38's low nibble with byte 33's low nibble.

  `0x14CD6` assigns byte 40 = 4. `0x13338` / `0x13340` copy bytes verbatim.

## Initialization differences

- `0x95B7..0x95C4`: clears all 40 bytes; `0x95C6`, `0x95CD` set binary
  variant and paired category byte to 1. This belongs to the sibling setup.
- Non-null-name branch `0x4DED..0x4DFC`: clears all 40 bytes, then
  `0x4DFE..0x4E19` copies the supplied C string **including NUL, without a
  local length bound**; `0x4E2C` stores the supplied availability mask.
  It does not assign the sibling's two defaults of 1.
- Current setup randomizes only the four selectors at `0xC4B8..0xC541`.
  Therefore zeros outside the identified fields are initialization evidence,
  not a universal wire constraint: the `0x4DED` incoming string copy and
  prior object state must be considered. Current four-way setup resets the
  selector and advances past unavailable choices at `0xCCC8..0xCD0F`;
  the all-four-unavailable case reaches 4 without a local clamp.

## String encoding

**Strong inference: intended name encoding is Windows CP950 / Big5. Proven:
the wire carries the input buffer's raw narrow bytes, without conversion in
the inspected getter/copy/builder chain. Runtime ACP is not pinned by this file.**

- Getter `0x165D0` counts/copies bytes. UI traversal calls `CharNextA`
  at `0x16589`, `0x166B6`; import-name thunk RVA `0x17F6A4` references
  name RVA `0x180806`, corresponding to IAT RVA `0x1706A4`.
- IME read `0x17F68` -> `0x143E70` -> IAT RVA `0x1701BC` is
  `ImmGetCompositionStringA` (name RVA `0x17FABC`). This is an ANSI input
  path, not evidence that every host's ACP must be 950.
- Name validator compares bytes `A1 40` at `0xAE91`, `0xAE97`, the CP950
  encoding of U+3000. Reserved-name pointers at `0x18409C..0x1840D8`
  include `A2 EF A2 F5` at `0x1846F8` (U+FF47 U+FF4D, fullwidth gm)
  and `A2 D5 A2 DB` at `0x1846F0` (U+FF27 U+FF2D, fullwidth GM).
- Numeric CP950 constants also appear in conversion helper `0x12F170`
  (`0x12F1A9`, `0x12F1BE`) and reverse helper `0x12F330`
  (`0x12F451`, `0x12F471`); these convert between 950 and 936.
  They are not calls in the inspected name-send chain.
- Crucially, `0xAD70` validation is called by the sibling submit at
  `0xAC09`; current submit `0xD0C1..0xD102` does not call it. Its literals
  support intended encoding but do not prove current client enforcement.

Persistence consequence: retain original name bytes alongside any CP950
decoded name; count encoded bytes for the 14-byte limit. Store the proven
numeric selections under neutral names plus raw profile data, preserve
unresolved bits, and do not give bytes 41..43 entity-field semantics.

## Final bounded follow-up: opcode 07 list projection

Define `L` as the response payload after opcode 07, `W_i = L+2+36*i`
as one wire record, and optional output `O` with record `A_i = O+4+40*i`.
These are distinct from create profile `C = main+0x15280` above.

### Exact receive and optional conversion

- `0x148BD` takes source packet+1; `0x148C0` sets 18 dwords;
  `0x148C7` / `0x148C9` copy **74 bytes**, i.e. two header bytes and
  two 36-byte record slots. `L[0]` is the loop count. `L[1]&1` is stored
  in network-object `+0x4200` at `0x1494E..0x14956`.
- `0x148CB..0x148D1` checks the optional output pointer. When non-null,
  `0x148D3..0x148DE` zero 124 bytes (`4+3*40`), then `0x148E0..0x148E2`
  assign `O[0]=L[0]`; the other three header bytes remain zero.
  The larger output allocation does **not** establish three valid wire
  records: this handler copied only two. There is no local count clamp.
- `0x148EC` sets EBX=`O+32`, `0x148EF` sets EDX=`L+18`.
  At each iteration, `0x148F2` selects the wire name and `0x148FA`
  selects `A_i`. `0x1490F` advances source by 36 and `0x14919`
  advances destination by 40. Accounting for those advances gives:

| Source within wire record W | Destination within 40-byte A | Copy RVAs |
| --- | --- | --- |
| Name at W+0, conventionally occupying W[0..15] | A+0, copied through first NUL, remaining bytes stay zero | scan `0x148FD`; copies `0x14915`, `0x1491F` |
| W[16] / tail[0] | A[28] | read `0x14921`, write `0x14924` |
| W[17] / tail[1] | A[29] | read `0x14927`, write `0x1492A` |
| W[18] / tail[2] | A[32] | read `0x1492D`, write `0x14930` |
| W[19]&7 / tail[3]&7 | A[34] | read `0x14933`, mask `0x14936`, write `0x1493A` |
| W[19] bits 3..7 and W[20..35] / tail[4..19] | Not copied | complete loop ends at `0x14946` |

For a well-formed name terminated within its 16-byte area, A[16..27],
A[30..31], A[33], A[35..39], and bytes after the name NUL are zero.
There is **no fixed 16-byte name memcpy** and **no 20-byte tail memcpy**
in the optional converter: its name scan is unbounded. Sending a NUL
within W[0..15] is therefore necessary; the create name's 14-byte bound
already leaves room. The sibling 07 handler has identical projection at
`0x146C8..0x14765`, with name copies `0x14724` / `0x1472E` and field
writes `0x14733`, `0x14739`, `0x1473F`, `0x14749`.

### Which representation the application uses

- Main selection caller `0xB490` supplies a null optional output at
  `0xB4AE` (EAX was zeroed and used for memset), raw list pointer
  `main+0x178CE0` at `0xB4AF..0xB4B5`, then calls `0x147D0` at `0xB4CC`.
  Consequently this path retains and consumes the **raw 36-byte list**.
- Alternate caller `0xF6A0` supplies raw and projected output pointers
  from its object `+0x664` / `+0x668` at `0xF6C7..0xF6D7`, call `0xF6EE`.
  Projected byte A[34] is subsequently read at `0xF425` as
  `O[4+40*selected+34]` and passed to `0x14C50` at `0xF43E`.
- Raw selection UI computes stride 36 at `0x7F7D..0x7F90` and limits
  its display index to 0/1 at `0x7F73`. Names come from W+0 at `0x8142`.
  It reads W[17] and computes `(value-1)/2` at `0x8167..0x8179`.
  Packed UI selectors are read directly from W word 20 at `0x8067`,
  `0x8093`, W word 22 at `0x80B0`, `0x80DE`, and W[24] low nibble
  at `0x8050..0x805D`. These bytes are absent from the optional projection.
  W[19]&7 is also consumed directly at `0xBA13..0xBA2F`.

### Reversibility and persistence consequence

The exact optional conversion is **not reversible**: it loses 16 tail
bytes, five bits of W[19], and name padding. A partial right-inverse for
a valid projected A is: copy its name through NUL into zero-padded W[0..15],
set W[16]=A[28], W[17]=A[29], W[18]=A[32], and W[19]&7=A[34].
W[19]'s upper bits and W[20..35] remain undetermined. Setting those to
zero would be a construction policy, not recovery of original bytes.

The optional A is **not established as the original create C** merely
because both have stride 40: it clears A[36..39], where C stores packed
selectors, and writes A[34], not C's binary variant at C[33]. Therefore
applying the partial inverse blindly to a stored create payload is not
a proven create-to-list serializer.

There is limited UI correspondence, explicitly **inferred from matching
consumers, not demonstrated by a copy**: create wire C[29] and W[17]
use the same paired-category arithmetic; C word 36 bits 0..7 and W word
20 bits 0..7 feed equivalent image/variant controls; C word 38 bits 4..15
and W word 22 bits 4..15 feed equivalent two graphic controls; C[33]
and W[24]'s low nibble select equivalent resource banks. These comparisons
do not recover the rest of the 20-byte tail or establish domain labels.

Result: exact 07-to-optional-40 mapping recovered; a complete, lossless
07 record cannot be recovered from that projection, and a complete exact
07 serializer from create C alone is not established by this bounded trace.
Preserving original raw W records preserves the otherwise discarded data.
No production implementation, account/session changes, or gameplay research.
